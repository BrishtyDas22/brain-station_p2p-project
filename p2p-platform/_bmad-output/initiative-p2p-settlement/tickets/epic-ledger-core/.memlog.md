- (decision by po) D1 reconciled (H-6 ledger status immutability): recommend removing status from ledger_entries. The specification contradicts itself - 4.2 and 14.1 say entries are never updated and no UPDATE exists against the table, while 3.1, 7.3 and 9.4 rely on a status column, and 5.1 lists status inside the hashed body. A mutable column inside a hash is a contradiction. The sweeper's function and 30s TTL are preserved; only the predicate changes from a column saying so to a record being absent. Does NOT block Epic 1. H-6 stays Proposed (not approved)
- (decision by po) D2 reconciled (A11 chain-finality POSTED lifecycle): recommend keeping the POSTED write outside the chain-close ACID unit and after the ACK. This dispute dissolves on reading the spec - 7.4 already orders COMMIT then ACK then UPDATE status. A11 is spec-verbatim, not a deviation. The stale-projection window is tolerable because 4.3 makes status a rebuildable projection and the ledger wins. The opposite choice would add a third row write inside the 1ms-budgeted closest transaction and buy nothing. Does NOT block Epic 1
- (decision by po) D2 consequence recorded: because finality is evidenced only by the close record, chain_close_records must be queryable by entry_id alone (the sweeper's predicate) as well as carrying UNIQUE (transaction_id, entry_id), a monotonic chain_position, and append-only protection. The reconciler must derive chain-closedness without reading transactions.status
- (decision by po) D3 reconciled (A7 reversal transaction modelling): recommend the reversal owns its own transactions row with reversals.original_transaction_id UNIQUE. The spec settles it by implication - 6.4 appends a new compensating pair while 10.2's Invariant 1 requires exactly one DEBIT and one CREDIT per transaction_id, so reusing the original id would make the spec's own nightly invariant fail on every successful reversal. Does NOT block Epic 1; reversals is Epic 4
- (decision by po) D3 consequence recorded: the original transaction becomes REVERSED while the reversal's own transaction runs the ordinary INITIATED to POSTED path. The two statuses are different things and must not be conflated in Epic 4
- (decision by po) D4 reconciled (A8 audit-outbox ordering): recommend keeping the outbox pattern - intent atomic with the money, chain append asynchronous. The audit intent commits with the money so suppressing the ledger write requires suppressing the same database write, and the ledger never blocks on the audit sink. The residual commit-to-drain window is bounded by the worker poll interval and the backlog is monitored. Does NOT block Epic 1
- (decision by po) D4 consequence recorded: audit_outbox carries scalar identifiers only and NO foreign key to any hot-path table, so an outbox insert can never participate in a lock-order inversion with the money path

## MICRO-LENDING WORKFLOW — `add-micro-lending-workflow` (not an Epic 1 story)

- (decision by po) The platform was built as a **peer-to-peer transfer** system, but the PRD is a **micro-lending** product: borrowers request a loan, lenders fund it from their own balance, the capital sits in escrow until the listing is fully funded, the principal disburses to the borrower's wallet, and the borrower repays in installments that are split back across the lenders. That flow did not exist, and the "Send Money" page that stood in its place was a disabled bKash/Nagad/Bank/Card dropdown that could never complete
- (decision by po) The **"Send Money" page, its route and `DemoController::send()` are DELETED, not disabled.** Leaving a dead payment dropdown in place misrepresents what the platform can do, and on a lending platform it suggests a member can send money to a peer — a different thing from funding a loan, with different rules. The `receive` and `notifications` screens remain read-only, and `receive` now states accurately how money reaches a member: a disbursed principal, a repayment share, or an Add Money top-up
- (decision by po) **The funding path involves NO EXTERNAL PAYMENT GATEWAY.** Funding a loan is not a payment — it is the movement of capital already inside the platform from a lender's balance into custody. The PRD's lender persona "commits funds toward single or syndicated micro-loans" from their wallet balance, so no payment-method selection is presented to a lender at all
- (decision by po) **The money path is IMPLEMENTED; the policy around it is NOT INVENTED.** Where the PRD names a rule it is used verbatim: the loan range BDT 5,000–50,000, the `MARKETPLACE_LISTED` / `ESCROW_LOCKED` / `DISBURSED` / `REPAID` status set, the 3-day `GRACE_PERIOD`, the 0.5% daily late penalty after grace expiry, proportional principal/interest distribution, and "database-level pessimistic locking on loan objects during funding calls to prevent race-condition overfunding". Where the PRD is **silent**, nothing is invented — no rate schedule, no risk score, no funding window, no restructuring/write-off/collection policy, no notification provider, no batch job
- (decision by po) **The interest rate is a BORROWER-STATED FIELD, not a computed one.** The PRD requires the rate to be *displayed* and the schedule to be *calculated*, but it defines no rate schedule, no risk-based pricing table and no default rate. Inventing one would be inventing financial policy. The rate is therefore stored as an integer number of basis points the borrower declares, bounded by a sandbox ceiling, and the schedule is computed from it with integer arithmetic only. The missing rate schedule is recorded as a deferred item with its blocker
- (decision by po) **H-1 is NOT APPROVED by this change.** Two more SYSTEM roles are added to the same unapproved umbrella — `ESCROW` for custody and `PAYOUT` for the external sink — and both are used only inside the local, development-only sandbox that `add-sandbox-wallet-funding` established. `C-4` remains unresolved. `C-3` remains ⚪ Open: the enforced limits are platform limits that mirror the PRD, not regulatory ceilings
- (decision by po) **The four SYSTEM roles are three different things, and the design recognises it.** `FUNDING` is the **source** — debited only, `balance_after` = cumulative amount sourced. `ESCROW` is **custody** of real user capital — credited and debited, `balance_after` = a genuine running balance (`SUM(CREDIT) − SUM(DEBIT)`) that can never go below zero. `PAYOUT` is the **sink** — credited only, `balance_after` = cumulative amount paid out. `TREASURY` is reserved and unused. `FUNDING` and `PAYOUT` are a matched pair: the outside world's wallet, from the platform's point of view
- (event by po) The credit rule in `LedgerPostingService::postPair()` was **widened, and carefully**. It previously refused to credit ANY system account, because crediting `FUNDING` would create money with no external inflow behind it. It now reads: a system account may be credited **only** if its role is `ESCROW` or `PAYOUT`, **and** only from a real user wallet. The second half is the part that matters — crediting escrow or payout from another system account would be money from nowhere, while crediting them from a user wallet is real user capital moving into custody or leaving the platform
- (decision by po) **A commitment is ONE balanced pair; the disbursement is a SECOND.** Commitment: DEBIT the lender's ledger account, CREDIT escrow, equal magnitude, one `transactions` row, `SUM(DEBIT) = SUM(CREDIT)`. Disbursement at 100%: DEBIT escrow, CREDIT the borrower's ledger account, a second balanced pair, a second `transactions` row. They are separate because they happen at different times for different reasons — one is a commitment, one is a release — and each must be independently auditable
- (decision by po) **Overfunding is PREVENTED IN CODE, at the database level.** The PRD's non-functional requirement is explicit: "database-level pessimistic locking on loan objects during funding calls to prevent race-condition overfunding". `LoanService::fund()` takes a `SELECT ... FOR UPDATE` on the loan row inside the funding transaction, so the second lender's read happens after the first lender's write has committed. Three further guards back it up: the escrow account is unsigned and cannot be debited below zero even if the lock were removed; the unique `idempotency_key` makes a replayed request a no-op; and a lender's wallet cannot go negative. A unique index on `(lender_user_id, loan_request_id)` additionally prevents the same lender funding the same listing twice
- (decision by po) **The installment schedule sums EXACTLY, and the distribution is EXACT.** The schedule is `tenure` equal installments with the last one absorbing the rounding remainder, so the installments sum to exactly the total repayable. Each collection is split across the lenders by `intdiv(installment_amount × lender_commitment, total_committed)`, and the truncation remainder goes to the **largest** commitment, so the installment is distributed exactly — no Poisha is created and none is lost
- (decision by po) **No real credential is EVER COLLECTED OR STORED, and the simulated outcome is CLEARLY DISTINGUISHED from a real one.** The client sends an *intent* (`CONFIRM` / `FAIL` / `CANCEL`), never an outcome, and the server maps it to a terminal state — there is no provider, so there is no provider confirmation to represent. A bank account is reduced to its last four digits before storage; there is no field for a PIN, an OTP, a password or a full card number. The sandbox is stated **once, in the page chrome, outside the payment interface**, and **only** on the screens where an external payout is simulated — the marketplace, the funding screen and the loan detail page carry no sandbox label, because they move real internal money between real internal wallets
